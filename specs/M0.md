# M0 Specification: research and feasibility

## Objective

Verify PAL RMGP01 Rev 0 inputs, reference sources, toolchain constraints, controller patch composition, and an online-only architecture using official unmodified Dolphin.

## Verified research and evidence

- Rust DOL parser/differ and PAL revision validation are implemented with synthetic tests.
- Official DolphinTool verified the supplied image as PAL RMGP01 revision 0; the RVZ was read-only.
- Dolphin 2609a GDB supports development memory operations but pauses at startup; no numeric stock performance comparison has been measured.
- MemoryWatcher is excluded from Windows 2609a and is one-way on Unix. Gecko can execute guest code but does not inherently expose host IPC.
- The former Dolphin source patch/build pipeline is retired. See [stock bridge feasibility](../docs/stock-dolphin-bridge.md).
- Product architecture is online-only, one official Dolphin per player; no Dolphin NetPlay or local split-screen.
- AllStars and shoulder-swap patch composition is externally supplied and statically checked; runtime gameplay compatibility is not claimed.

## Functional requirements

- Fail closed for unknown PAL revision/hash/symbol maps and patch conflicts.
- Keep AllStars mandatory, third-party files external, Rust-first, and client localization separate from gameplay data.
- Establish whether official Dolphin can support a low-overhead bidirectional bridge before implementing online game-state synchronization.

## Technical design

Rust workspace owns patch analysis, launcher, protocol/networking, deterministic data types, and tests. Verified PPC/Gecko/DOL hooks may provide guest logic, but a stock-compatible host communication channel remains an open question. No Dolphin source modifications or custom binary builds are allowed. Never infer addresses or APIs.

## Dependencies

Rust/Cargo; user-supplied legal PAL files; verified symbols/revision; official Dolphin; PPC disassembly/injection toolchain; external AllStars files; interactive Windows gameplay session for runtime tests.

## Risks

Stock Dolphin may lack suitable host IPC. GDB overhead is unquantified. Game actor lifecycle, singleton assumptions, progression, locale asset effects, third-party licensing, and Rust Wii ABI/linking remain unresolved.

## Acceptance criteria

Document exact verified research, set stock-only architecture, validate PAL input with official DolphinTool, and specify a stock bridge experiment with measurable cadence and gameplay performance gates. M0 remains in progress until bridge feasibility and required interactive tests are addressed.

## Testing strategy

Run Rust workspace unit tests and read-only PAL revision validation. Runtime bridge testing must use a visible interactive Dolphin process and distinguish game boot, patch activation, memory reads, and actual two-way state exchange.
