# Blender Animation Retargeting Tooling Specification

## Scope and placement

This worktree contains no existing DCC or animation tooling. The bridge belongs in `tools/blender/`, separate from the Rust multiplayer crates and proprietary assets. Its first milestone is a local inspection and experiment harness. It does not retarget complete animation sets or claim in-game validation.

## Architecture

`tools/blender/bridge.py` runs inside Blender and exposes a versioned JSON-lines TCP protocol on loopback only. A socket thread handles framing and queues requests; a Blender timer executes all `bpy` operations on Blender's main thread and returns structured JSON. `tools/blender/client.py` is a standard-library command-line client. Requests carry protocol version, request id, operation, and arguments. Responses carry matching id, success/error, and result. A single request per connection keeps framing simple. Bind explicitly to `127.0.0.1`; reject non-loopback peers. No authentication is intended because the service is local-only; do not bind to wildcard/LAN addresses.

## Safety rules

Inspection operations are read-only. Mutation operations use a distinct `mutate.*` namespace and require explicit arguments. Experimental objects receive a bridge ownership tag and unique names. The bridge never applies object transforms or deletes arbitrary objects/actions. Cleanup can remove only bridge-tagged experimental objects and actions, and reports every removal. Before creating test duplicates, preserve the originals by duplicating object and armature data; never mutate the source. Never overwrite `Waluigi_GalaxyWalk_Legs_Baked`; experimental actions must have new names. Avoid broad `bpy.ops.object.select_all` and global deletion patterns. Source asset files are never read for writing.

## Blender bridge and API

The first API provides:

- `inspect.objects`: object names, types, data names, transforms, and tags.
- `inspect.armature`: bones, parent names, rest matrices, head/tail, connected/deform flags.
- `inspect.weights`: mesh vertex groups with nonzero weighted counts and totals, optionally limited to named bones.
- `inspect.actions`: actions, slots/layers/strips/channelbags and fcurve metadata; legacy `action.fcurves` is inspected when available. Keyframes and data paths are included, not evaluated as scene changes.
- `inspect.pose`: evaluate a named armature at an arbitrary frame, capture pose matrices and basis matrices, then restore the previous scene frame.
- `analyze.waluigi_arm`: read-only left-arm analysis of rest geometry, custom metadata, mesh weights, action channels, sampled local/armature/world rotations, sign-invariant angular displacement, and pairwise relative orientation changes. Named actions are evaluated on a temporary armature/data duplicate, so the analyzed rig's assigned action is never replaced. Weight meshes can be supplied explicitly to avoid mixing unrelated scene meshes.
- `mutate.duplicate_rig`: make an isolated armature object/data copy with a unique experiment name and bridge ownership tag. It does not copy or rebind meshes.
- `mutate.restore`: remove only tagged experimental objects and bridge-created actions; it never touches untagged data.

Errors are structured and fail closed for absent or ambiguous names. Matrices use nested row-major numeric arrays. Inspection output avoids Blender RNA objects and is JSON serializable.

## Retargeting pipeline

1. Inspect and fingerprint source/target armatures, rest matrices, hierarchies, mesh weights, and source action curves.
2. Save an explicit inspection report before experimentation.
3. Duplicate target armature/data into a tagged test rig; author experimental actions under unique names.
4. Solve mapping and constraints in an isolated experiment, evaluate at requested frames, and bake only onto the duplicate.
5. Compare pose matrices and capture reports or viewport renders for visual review.
6. Promote results manually after validation; this milestone does not automate promotion.

For the immediate arm research target, first characterize native Sluggers angular trajectories, relative transforms, and glove/forearm deformation for bones 22, 23, 24, 25, 26, 27, 29, and 30. Existing validated leg bake and torso observations remain inputs and are not regenerated by this tooling.

## First left-arm walk prototype

The first prototype accepts only the explicit `luigi.001_armature_walk` source action and a disposable Waluigi test armature. It duplicates the source rig for action evaluation, duplicates the target armature and explicitly named weighted meshes, and rewires only duplicated mesh armature modifiers. The production Waluigi object and source rig are never assigned a new action or pose.

On the main branch, source local pose rotations are conjugated through source/target relative rest-bone orientations and applied as target local FK. The mapping is `ShoulderL→bone_23`, `ArmL1→bone_24`, `ArmL2→bone_26`, `HandL→bone_27`; unweighted bridge bones 22 and 30 retain identity local deltas. On the overlap branch, `ArmL1→bone_25` and `HandL→bone_29` are driven from their own source evaluated armature-space rest-relative deltas and solved into the duplicate target pose. This deliberately maps separate source joints onto the overlapping weighted regions so the 23/25 and 26/29 pairs retain changing relative motion. No constraints are used.

The prototype keys integer frames 0–60 into a newly named Blender 5 layered action, including location, quaternion rotation, and scale channels for the eight arm bones. It does not alter fingers or the validated leg action. Duplicated test meshes are skinned to the duplicate armature for numerical deformation diagnostics. The client writes before/after transforms, joint gaps and their change from baseline, weighted-region centroids, object/bone scales, constraint counts, branch-relative orientation changes, and finite-number checks to a JSON report. A visual review of the duplicate remains required before right-arm or full-body work.

Live prototype report: `tools/blender/reports/waluigi_left_arm_prototype.json`. Created `Waluigi_Arm_Retarget_Prototype` with action `Waluigi_LeftArm_Retarget_Prototype` and two `_ArmRetargetPreview` meshes. Finite values, object/mesh/bone scales, and zero runtime constraints all pass. Main elbow and wrist/glove endpoint gaps remain zero; overlap elbow maximum is 0.000018 world units. The shoulder gap is 6.13836 world units on the original test rig and changes by at most 0.0000048, so continuity is preserved relative to baseline despite the existing offset. Branch-relative orientation changes reach 50.70° for bones 23/25 and 138.66° for 26/29. Submesh0 contains the weighted groups; submesh1 reports zero arm-bone weights. The large branch motion and mesh-region movement remain visual risks, so do not treat these numeric checks as visual acceptance.

## Validation strategy

Run Python protocol/helper tests without Blender where feasible, and Blender background smoke checks when Blender is installed. Exercise protocol version/errors, loopback binding, hierarchy/matrix serialization, layered action inspection, arbitrary-frame evaluation with frame restoration, duplicate ownership tags, and scoped cleanup. In Blender, verify the bridge does not alter original object/data names, transforms, actions, or the existing baked walk action. Visual review remains a separate Blender UI step. Passing tests does not establish animation quality or game integration.

The standalone quaternion tests cover normalization, q/−q equivalence, relative rotations, and correlation of angular-displacement sequences. Blender 5.2.3 background smoke tests and the live `sequence_10.003` comparison pass. Sampled the action range `[0, 13.6667]` at 100 evenly spaced frames. The integer-only 0–60 probe under-sampled the action's subframe keys; a 100-sample pass reproduced the prior maximum angular displacements within 0.03°: `22:100.98°, 23:104.01°, 24:16.64°, 25:103.21° (manual 103.19°), 26:132.90°, 27:23.92° (manual 23.91°), 29:131.62°, 30:85.33°`. Weighted vertex counts matched exactly: `22:58, 23:49, 24:0, 25:29, 26:0, 27:54, 29:59, 30:104`. Local angular-displacement correlations measured `23↔25:0.9690` and `26↔29:0.9758` (manual `0.969` and `0.976`).

The relative-orientation samples match the manual values exactly at frames 2, 5, 8, and 11: `23↔25:19.377°, 24.504°, 20.829°, 20.921°`; `26↔29:25.052°, 24.374°, 27.746°, 33.468°`. Across the full 100-sample range, the maximum relative changes were `34.40°` and `35.81°`. These values confirm both pairs move with high correlated displacement while changing relative orientation, so neither pair is rigidly coupled.

Rest-angle output currently measures each parent/child bone's longitudinal rest axes. It reports `23→24:0.000°`, `24→26:0.588°`, and `26→27:0.000°`; also `22→23:0.213°` and `27→30:3.276°`. This differs from the previously recorded `23→24:0.213°`, `24→26:0.587°`, `26→27:0.588°`, which used a different vector construction. Preserve both definitions in future geometry reports instead of treating the values as interchangeable. The independently measured virtual endpoint distances do match: `bone_23.head→bone_26.head:23.608`, `bone_26.head→bone_30.head:26.028`, ratio `0.9070` (with the intentional 43.437 object scale included in the distance calculation).

The armature has TrackId metadata: `bone_22:16, 23:115, 24:116, 25:17, 26:111, 27:112, 29:18, 30:19`. The two branches have separate TrackId ranges: `22→25→29→30` uses `16,17,18,19`, while `23→24→26→27` uses `115,116,111,112`. This is useful provenance but does not by itself establish animation coupling or retarget behavior.

Recommended first safe retargeting prototype: on a duplicate test rig only, apply rest-calibrated FK rotations to the main branch and separately drive overlap bones from their mapped source joints. This Milestone 2 implementation uses `ShoulderL→bone_23`, `ArmL1→bone_24/bone_25`, `ArmL2→bone_26`, and `HandL→bone_27/bone_29`; bridge bones 22 and 30 retain identity local deltas. Preserve changing relative orientation; do not collapse either pair to a rigid link or solve only the hand endpoint. Bake evaluated matrices to a new experiment action and inspect all weighted regions across the action range before considering any integration.

## Failed FK prototype and coupled-model design

The live `Waluigi_LeftArm_Retarget_Prototype` is a failed experiment. Viewport inspection showed twisting/collapse across the whole walk, divergent branches, wrong elbow anatomy, and a detached glove. It must not be tuned or promoted. The first mapping assigned Luigi joints directly to individual Waluigi bones and treated unweighted structural bones as if they were anatomical joint pivots. It had no objective for weighted mesh deformation or for matching the coupled native branch pose. Independent F-curves did not make the mapping anatomically independent; the selected source joints drove incompatible rest geometry. The output diagnostics at `tools/blender/reports/waluigi_left_arm_prototype.json` record finite values, constant scales, zero constraints, and small hierarchy endpoint gaps, but those checks did not detect the visual collapse. They are necessary checks, not sufficient acceptance criteria.

### Read-only native-action evidence

`tools/blender/study_native_arm.py` samples several Sluggers actions without changing the rig. The checked set is `sequence_10.003`, `sequence_12.001`, `sequence_15.001`, `sequence_4.001`, and `sequence_8.001`, with 41 evenly spaced samples per action. Results are saved in `tools/blender/reports/native_arm_multi_action_study.json`.

Across these clips, sign-invariant local angular-displacement correlations remain high but are not fixed: bone 23/25 correlations range `0.913–0.994`, while their maximum relative orientation changes range `9.2–83.6°`; bone 26/29 correlations range `0.899–0.999`, with relative changes `11.4–35.4°`. The main and overlap elbow-head landmarks also separate by `5.17–19.98` world units, and the main glove head versus the overlap forearm tail spans `17.7–27.3` world units. These are native deformations, not targets to force to a shared endpoint. Bones 24 and 26 have no vertex weights but carry structural motion between weighted regions. TrackIds remain consistent across actions: 22/25/29/30 are `16/17/18/19`; 23/24/26/27 are `115/116/111/112`.

This evidence supports a **coupled native deformation calibration**, not a per-bone rotation copy:

1. Define a canonical semantic limb state `s = (R_shoulder, θ_elbow, θ_forearm-roll, R_wrist, p_hand)` relative to torso and normalized by limb length. Keep shoulder orientation, elbow flexion, forearm axial roll, wrist orientation, and hand position distinct.
2. For every native sample, encode the complete arm pose as rest-relative SE(3) logarithms for bones 22, 23, 24, 25, 26, 27, 29, and 30. Include branch-relative residuals and weighted mesh landmarks; do not constrain the two elbow estimates to coincide.
3. Fit a shared low-dimensional native pose manifold `z = μ + B α`, where `z` contains all deform-bone transforms and `α` is predicted from semantic state, its velocity, and motion-family context. Shared coefficients make both branches move together where native examples do, while learned residuals preserve their changing relative rotations and landmark offsets.
4. Retarget a source semantic trajectory by solving for `α_t` over time, minimizing semantic endpoint/orientation error, distance to the learned native manifold, weighted-region deformation error, and temporal acceleration. Use soft branch landmark terms learned from native samples rather than hard endpoint IK.
5. Bake all target transforms to a new action on a disposable duplicate. Validate held-out native actions and source motions using weighted-vertex positions, joint/branch residuals, scale/NaN checks, and visual review.

The retarget engine should consume a character-neutral semantic trajectory and a target calibration profile. Luigi and Mario source adapters produce the same semantic state; Waluigi and Wario profiles contain their own rest transforms, weights, and learned deformation manifold. This keeps the solver reusable for Luigi→Waluigi and Mario→Wario instead of embedding Waluigi bone names into the generic math.

The five-action study is exploratory rather than sufficient training data. The next calibration set needs clips that independently cover shoulder elevation/protraction, elbow flexion, forearm pronation/supination, wrist deviation, and hand orientation, plus combined motions and repeated cycles. Preserve exact keyframe/subframe times, source action slot identifiers, TrackIds, rest transforms, and evaluated deformed mesh vertices/weighted landmarks. Add motion-family/phase labels so native branch style is identifiable. Split by action for held-out validation; frame-level random splitting would leak nearly identical poses across train and validation. The current sequence names are not semantic labels, and the varying branch residuals cannot yet be predicted from source semantic state alone.

## Limitations and future extensions

The bridge is trusted local development tooling, not a hardened network service. Meshes are not rebound to duplicates in the first milestone. Full retargeting, baking, rendering, provenance fingerprints, and MCP wrapping remain future work. An MCP adapter may translate tool calls to this versioned local protocol without gaining direct Blender access.
